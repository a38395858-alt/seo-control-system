# 开发卡：P6.6 遗留数据收口与全表覆盖

状态：已完成（2026-07-31）

## 目标

收口 P6.2-P6.5 之后剩余的一方知识、旧竞品研究、定时学习、URL 归档、权威资料搜索和持久任务数据，并用自动化覆盖审计证明每张 SQLite 业务表都有迁移归属或明确的安全排除理由。

## 固定迁移顺序

1. `project_knowledge_documents`
2. `project_knowledge_crawl_runs`
3. `project_knowledge_crawl_pages`
4. `authority_search_results`
5. `authority_url_exclusions`
6. `competitor_learning_schedules`
7. `competitor_learning_runs`
8. `competitor_style_cards`
9. `competitor_research_runs`
10. `competitor_research_items`
11. `competitor_url_archive`
12. `durable_task_queue`

## 项目隔离与恢复

- 12 张 PostgreSQL 目标表均显式保存 `project_id`。
- 知识爬取页通过 Crawl Run 推导项目；竞品研究条目通过 Research Run 推导项目。
- 旧竞品调研引用 P6.4 的竞品正文目标表，权威搜索引用 P6.5 的内容资产目标表。
- 持久任务保留 `status`、`attempt_count`、`available_at`、`lease_expires_at`、`celery_task_id` 和最后错误；切换时由 Worker 恢复到期任务。

## 明确排除

- `schema_migrations`：SQLite 自身版本历史，PostgreSQL 使用独立 DDL/版本管理，不复制。
- `gsc_oauth_connection`：包含 refresh token 且是全局连接，不进入快照、日志或 mismatch 报告；新环境重新 OAuth 授权。

## CLI

```text
migrate-legacy-postgres [--apply]
validate-legacy-postgres
```

dry-run 只读 SQLite，不连接 PostgreSQL。apply 按固定依赖顺序在单事务中批量 upsert。

# SEO 内容自主 Agent：开发环境与模块化实施总规划

> **文档目的**：将 SEO 内容自主 Agent 拆分为可独立开发、测试、验收和上线的环境与功能模块。本文是后续开发的总入口；模块实施时不得跨越本文定义的边界。
>
> **当前基线**：React 静态前端 + Python HTTP 服务 + SQLite，工作台地址为 `http://127.0.0.1:8000`。
>
> **核心方向**：同行域名与关键词采集是学习主来源；公司资料是事实与品牌边界；GSC 是发布后的效果与锚文本反馈，不是竞品学习主来源。

---

## 1. 环境拆解

### 1.1 当前开发环境（必须保持可用）

| 层级 | 当前实现 | 责任 | 不承担的责任 |
| --- | --- | --- | --- |
| 前端 | React / Vite，构建到 `web/` | 页面、用户操作、状态展示 | 不直连数据库、GSC、WordPress 或模型 |
| 应用服务 | Python HTTP 服务，`src/seo_control/web.py` | API、权限、项目隔离、业务校验 | 不在请求线程中执行长任务 |
| 业务逻辑 | `src/seo_control/application/` | 采集、生成、记忆、发布业务服务 | 不直接面向浏览器 UI |
| 数据 | SQLite | 项目、内容、记忆、任务、审批、日志 | 多机并发任务队列 |
| 静态部署 | Python 服务提供 `web/` | 本地工作台 | 不替代后台 Worker |

当前阶段所有新功能必须能在 SQLite 环境工作，不能为了接入 Agent 破坏已有关键词、标题、内容、采集或 WordPress 功能。

### 1.2 目标运行环境（任务量稳定后启用）

```text
React 前端
    │ HTTP API
    ▼
Python 应用服务 ────── PostgreSQL（正式业务与任务数据）
    │
    ├──── Redis（队列、锁、限流、缓存）
    ▼
Celery Worker / Scheduler（采集、学习、写作、GSC 任务）
```

| 组件 | 何时引入 | 用途 |
| --- | --- | --- |
| PostgreSQL | 多项目/多 Worker 或 SQLite 写入竞争出现前 | 事务、并发、长期任务数据 |
| Redis | 开始执行持久化队列时 | 任务队列、去重锁、限流、缓存 |
| Celery Worker | 采集/学习/生成不能继续由 HTTP 请求执行时 | 后台执行、失败重试、恢复、并发控制 |
| Celery Beat / Scheduler | 启用每日/每周自主学习时 | 定时投递任务 |

迁移原则：先抽象 Repository、Task Queue 和配置接口；SQLite 与 PostgreSQL、单机 Worker 与 Celery 通过同一应用接口切换，不能让前端或 Agent 依赖具体基础设施。

### 1.3 推荐目录边界

```text
src/seo_control/
├─ web.py                         # HTTP 路由与请求校验，只负责适配层
├─ application/
│  ├─ agent_workflows/             # LangGraph 图、节点状态与恢复逻辑
│  ├─ agent_tools/                 # 模型可调用的白名单服务端工具
│  ├─ competitor_intelligence/     # 域名/关键词发现、正文采集、筛选
│  ├─ learning/                    # 写法卡、事实卡、记忆治理与召回
│  ├─ content_production/          # 蓝图、写作、QA、重写
│  ├─ publishing/                  # 发布前门禁、WordPress 草稿和确认发布
│  └─ performance_feedback/        # GSC 快照、锚文本、表现记忆
├─ infrastructure/
│  ├─ database.py                  # Migration、Repository 装配
│  ├─ repositories/                # SQLite / PostgreSQL 数据访问实现
│  └─ task_queue/                  # SQLite 队列适配器、Celery 适配器
└─ domain/                         # 项目、任务、记忆、内容等领域对象

frontend/src/
├─ pages/                          # 按业务模块组织页面
├─ features/                       # 模块 UI、状态、API 调用
├─ api.ts                          # API 客户端（后续按模块拆分）
└─ types.ts                        # 共享 API 类型（后续按模块拆分）
```

现有代码迁移采用“新模块新目录、旧接口渐进适配”的方式，不进行一次性重写。

## 2. 功能模块总表

| 编号 | 模块 | 用户入口 | 数据所有权 | 关键产出 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| M0 | 项目与集成中心 | 项目设置、AI 与集成 | 项目、权限、预算、连接配置 | 项目上下文 | 无 |
| M1 | 采集计划中心 | 竞品与资料采集 | 域名计划、关键词计划、采集策略 | 待采集 URL | M0 |
| M2 | 内容采集中心 | 采集竞品内容 | URL 目录、采集运行、正文版本、失败日志 | 合格内容资料 | M1 |
| M3 | 内容资料库 | 采集内容库、公司知识库 | 竞品正文、一方资料、来源元数据 | 可分析资料 | M2 |
| M4 | 内容理解中心 | 学习与写法卡 | 主题、写法卡、结构卡、选题缺口卡 | 受证据约束的学习卡 | M3 |
| M5 | 记忆治理中心 | 学习记忆与反馈 | 记忆、证据、置信度、时效、反馈 | 可召回长期记忆 | M4、M0 |
| M6 | 内容生产 Agent | 内容生产 | 蓝图、草稿、生成运行、QA、重写 | 待发布内容 | M5、M3 |
| M7 | 审批与发布中心 | 审核与发布 | 审批、发布前检查、WordPress 映射 | 草稿或已发布内容 | M6、M0 |
| M8 | GSC 与优化中心 | GSC 与优化 | 查询-页面关系、效果快照、锚文本建议 | 表现记忆、优化建议 | M7、M5 |
| M9 | Agent 调度与运行中心 | 系统任务、Agent 任务中心 | 运行、节点、检查点、重试、成本、审计 | 可恢复任务 | M0-M8 |

### M0：项目与集成中心

- 维护 `project_id`、网站域名、语言、品牌资料边界、AI 模型、预算、WordPress/GSC 配置。
- 所有 API、工具、任务和记忆必须先通过此模块校验项目归属。
- 不负责采集、生成或发布执行。

### M1-M3：采集与资料链路

采集主线统一为：

```text
同行域名计划 ─┐
              ├─ URL 发现/规范化/去重 ─ 内容提取/质量过滤 ─ 资料库
关键词采集计划 ─┘
公司知识库/网站资料 ────────────────────────────────────────┘
```

- **同行域名采集**：优先 Sitemap、文章目录、RSS 和已发现文章链接；只纳入文章型页面。
- **关键词采集**：从项目关键词库发现自然搜索结果，过滤广告、商品页、社媒、视频与自身网站。
- **一方资料**：公司知识库、产品资料、已发布文章、权威来源；与竞品内容分开标记。
- 每个 URL 保存规范 URL、来源类型、来源关键词/域名、正文哈希、版本、采集时间、状态与失败原因。
- 尊重 `robots.txt`；不读取登录内容，不绕过访问限制。

### M4：内容理解中心

输入是“合格资料”，输出必须是结构化卡片，而不是竞品正文副本：

- 写法卡：标题方式、解释顺序、段落深度、FAQ/表格/步骤等格式。
- 结构卡：某主题下的推荐信息架构。
- 选题缺口卡：竞品覆盖与本站现有内容的差异。
- 事实卡：仅来自一方资料或可验证权威来源；模型推测标记为待验证，不能升级为事实。

### M5：记忆治理中心

记忆类型：`style`、`structure`、`topic_gap`、`brand_fact`、`brand_voice`、`editorial_preference`、`performance`。

每条记忆必须拥有：来源、证据、来源时间、版本、适用范围、置信度、有效期、状态、权重和治理记录。

治理规则：重复合并；来源失效或过期降权；低质量待人工处理；人工多次否决则停用；模型推测不得保存为事实。

### M6：内容生产 Agent

固定链路：

```text
读取项目上下文
→ 检索记忆与资料
→ 生成内容蓝图
→ 等待人工确认蓝图
→ 生成文章
→ QA
→ 最多两次定向重写
→ 发布前门禁
```

每篇文章必须输出“生成依据报告”：使用哪些记忆、为何召回、来自何处、用了哪些已验证事实、哪些风险被拦截。

### M7：审批与发布中心

- 蓝图审批与公开发布审批是两个独立状态。
- WordPress 默认只创建草稿；公开发布必须由人工确认操作触发。
- 发布门禁检查高风险事实、重复风险、QA、标题/描述/Slug、链接、图片和项目归属。

### M8：GSC 与优化中心

- 采集当前项目查询、页面、点击、展现和排名快照。
- 输出锚文本、内链、内容补充建议。
- 在达到观察周期后形成表现记忆；只描述相关性，不宣称因果。
- 不作为竞品学习主来源，也不跨项目共享。

### M9：Agent 调度与运行中心

每个长任务都由 `run_id` 管理，节点状态统一为：

```text
queued → running → waiting_approval / paused / retry_wait / failed / cancelled / completed
```

必须持久化：任务输入输出、模型、提示词版本、耗时、成本、错误、重试次数、审批决定和断点。

## 3. Agent 工具边界

LangGraph 和模型只可调用以下服务端白名单工具，不能直连 SQLite、PostgreSQL、文件系统、GSC 或 WordPress：

```text
retrieve_project_memories
research_competitors
collect_competitor_content
collect_first_party_sources
extract_learning_cards
generate_content_blueprint
generate_article
review_article
prepare_publish
capture_gsc_performance
update_memory_governance
```

每个工具必须执行：

1. 校验 `project_id` 与当前 `run_id` 一致；
2. 验证输入结构、数量、并发、超时和预算；
3. 记录输入摘要、输出摘要、模型、成本和错误；
4. 使用幂等键，避免重复采集、重复学习或重复发布；
5. 对外部写操作检查审批状态。

## 6. 通用验收门禁

任意模块合并前必须满足：

- 项目隔离测试通过；
- API 与工具均二次校验 `project_id`；
- 失败、重试、取消和恢复路径有测试；
- 数据库变更有 migration，且不破坏历史数据；
- 前端有加载、空态、失败、重试与禁用状态；
- 长任务有日志、耗时、错误与状态显示；
- `python` 测试和 `npm run build` 通过；
- 真实页面完成浏览器验收；
- 无法绕过蓝图审批、发布审批、robots 或高风险事实门禁。

# 开发卡：P6.3 / M1-M3 关键词与采集 Repository 迁移

状态：已完成（2026-07-31）

## 目标

在不改变 SQLite 正式业务源的前提下，把关键词库读取/软删除、采集计划读取和竞品 URL 目录读取从 `web.py` 内联 SQL 抽离，并建立可预览、可幂等执行、可逐字段校验的 PostgreSQL 迁移镜像。

## 本阶段边界

- M1 关键词：迁移关键词主记录，以及当前搜索量、竞争度、分类、搜索意图、SEO 适配结论、已选标题和标题候选数的可验证快照。
- M2-M3 采集入口：迁移 `collection_plans` 与 `competitor_url_catalog`。
- API 继续强制 `project_id`，软删除不得影响其他项目。
- PostgreSQL 表必须引用已迁移的 `workspace_projects`，因此正式应用顺序固定为项目 → 关键词 → 采集。
- 所有命令未传 `--apply` 时只读取 SQLite 快照，不连接或写入 PostgreSQL。

## 暂不迁移

- 关键词导入批次、原始行、来源、历史指标快照、AI 审核历史与标题历史；本阶段只保留关键词当前可用快照，历史表后续单独迁移。
- 采集运行、URL 执行项、竞品正文、正文版本、学习卡和记忆来源；这些表与 M4 记忆证据链一起迁移。
- 不启用 SQLite/PostgreSQL 双写，不允许前端切换 PostgreSQL 数据源。

## PostgreSQL 目标表

- `workspace_keywords`
- `workspace_collection_plans`
- `workspace_competitor_urls`

三个表均保留 SQLite 原 ID、项目 ID、业务唯一键、创建/更新时间和 `migrated_at`。`memory_id` 在正文记忆模块迁移前只作为旧系统引用保存，不建立跨未迁移表的外键。

## CLI

```text
migrate-keywords-postgres [--apply]
validate-keywords-postgres
migrate-collection-postgres [--apply]
validate-collection-postgres
```

迁移报告必须包含源/目标数量、实际迁移数、缺失键、额外键、逐字段差异和是否有效。采集报告的实体键使用 `plan:<id>`、`catalog:<id>`，避免不同表 ID 冲突。

## 验收标准

- 关键词和采集读取 API 与改造前响应兼容。
- 关键词软删除保持项目隔离和二次确认规则。
- 两类迁移均支持 dry-run、重复 apply、缺失/额外/字段差异校验。
- PostgreSQL 不可用不影响 SQLite 工作台启动和使用。
- 真实数据库迁移必须先完成 P6.2 项目迁移，并在每批迁移后得到零差异报告。
- 全量 Python 测试、React 构建和项目 3 页面验收通过。

## 已交付

- 新增 `KeywordRepository`、`CollectionRepository` 及 SQLite/PostgreSQL 实现。
- `/api/keywords` 读取与软删除、`/api/collection-plans` 读取、`/api/competitor-url-catalog` 读取已改由 Repository 执行。
- 新增通用 `SnapshotMigrationService`，统一处理 dry-run、幂等 upsert、序列校准、缺失/额外键和逐字段差异。
- PostgreSQL 新增 `workspace_keywords`、`workspace_collection_plans`、`workspace_competitor_urls`，并通过 `project_id` 外键依赖 `workspace_projects`。
- 关键词快照保留当前聚合结果，同时保留软删除记录；API 仍只展示当前项目未删除关键词。
- 采集计划的 JSON 设置在校验时规范化，避免仅因键顺序或空格产生误报。
- CLI 已实现四个独立预览/应用/校验命令，未传 `--apply` 时不会连接 PostgreSQL。
